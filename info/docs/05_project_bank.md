**포지션 적합도:** 매우 높음

## B. 강력 추천 서비스/개인 프로젝트

### 4) WOL Docker
**상태:** 포함 추천  
**포지션 적합도:** 높음

#### 현재 파악된 내용
- 개인 프로젝트
- 네트워크 관련 개인 텀프로젝트
- 도커를 사용해 홈서버에 등록해 두고 WOL 기능을 통합하려는 시도
- Magic Packet 구조와 실제 패킷 전송 과정 검증
- 공유기 지원 여부 등 실제 네트워크 환경 제약 확인
- 원격으로 PC를 켜는 기능에 더해 사전 등록한 프로그램 실행 기능까지 고려

#### 왜 쓸 만한가
- 서비스성보다 **네트워크 환경과 실제 동작 조건을 확인한 점**이 좋음
- “코드만 짰다”가 아니라 **환경 의존성과 제약을 확인한 프로젝트**라는 점에서 설득력이 있음
- 네트워크/시스템/도커 경험을 동시에 연결할 수 있음

#### 주의점
- 완성도와 공개 범위는 과장 금지
- “기획만 했다”는 원문 메모와 “Magic Packet/환경 검증” 서사를 함께 반영해야 함

#### 카드 제목 예시
- `WOL을 실제 네트워크 환경에서 검증하며 배운 제약 조건`
- `코드보다 환경이 더 중요했던 WOL Docker 프로젝트`

### 5) Checkhouse
**상태:** 포함 추천  
**포지션 적합도:** 중간 이상

#### 현재 파악된 내용
- 팀 프로젝트
- React 기반으로 정리된 자료 존재, 자소서에서는 백엔드 담당으로 명시
- TDD/코드리뷰 도입 계획이 있었음
- 후반부에 검증되지 않은 AI 생성 코드와 리뷰 누락으로 구조적 불일치/실행 오류 누적
- 마감 직전 핵심 기능 위주로 우선순위를 나누고, 문제 코드를 구조부터 다시 추적/복구
- 최종 발표 및 시연 마무리

#### 왜 쓸 만한가
- **검증의 중요성**을 배운 사례로 매우 좋음
- 코드 리뷰, 테스트, 신뢰성, 구조 이해 같은 키워드를 자연스럽게 설명 가능
- 사용자 포지셔닝의 `코드 분석/검증` 성향과 맞닿아 있음

#### 주의점
- AI/팀원 탓 서사로 흐르면 안 됨
- “백엔드 담당” vs “프론트+백엔드 담당” 자료가 섞일 가능성 있으므로 최종 확정 필요
- 기술 스택/역할 범위를 정확히 다시 적어야 함

#### 카드 제목 예시
- `Checkhouse: 마감 직전 장애를 구조부터 다시 추적해 복구한 경험`
- `검증되지 않은 코드가 만든 문제를 정리하며 배운 테스트의 중요성`

### 6) Manbo
**상태:** 포함 가능, 협업 사례로 유효  
**포지션 적합도:** 중간

#### 현재 파악된 내용
- 산책로 공유 서비스 팀 프로젝트
- React Native + Spring Boot 자료 존재
- 프론트엔드 담당
- 프론트 2명이었고 둘 다 React Native 초심자
- 문서/강의 자료를 함께 보며 학습
- 일정 지연 시 우선순위를 재정리하고 역할 재분배
- 목표 기간 안에 주요 기능 완성

#### 왜 쓸 만한가
- **낯선 기술을 빠르게 학습하고 팀과 공유한 경험**
- 일정 압박 속 협업/소통/역할 조정 사례
- 포트폴리오에 인간적인 입체감과 팀개발 경험을 더해 줌

#### 주의점
- 메인 카드 1순위는 아님
- “결과적으로 내가 거의 다 했다” 식의 표현 금지
- 기술적 난점이나 맡은 기능이 정리되지 않으면 설명이 약해질 수 있음

#### 카드 제목 예시
- `처음 쓰는 React Native로 프로토타입을 완성한 협업 경험`
- `학습과 역할 재조정으로 일정을 맞춘 Manbo 프로젝트`

### 7) Family Community
**상태:** 조건부 포함  
**포지션 적합도:** 중간

#### 현재 파악된 내용
- 가족 간 소통을 늘리기 위한 프로젝트
- React / Spring Boot / Kubernetes 언급
- 웹 기반/웹앱
- 프론트 전반 담당
- 소켓 채팅 구현 언급
- 진행 중 프로젝트

#### 왜 고려할 수 있는가
- Kubernetes, 웹앱, 채팅, 팀프로젝트 등 키워드는 나쁘지 않음
- 다만 현재 메인 포지셔닝과 직접 연결되는 정도는 높지 않음

#### 주의점
- 진행 중이며 완성도/공개 범위 불명확
- “사실 바이브코딩함” 메모가 있어 본인 이해 범위를 넘겨 쓰면 안 됨

#### 포함 기준
- 공개 가능한 저장소 또는 데모가 있음
- 본인이 직접 설명 가능한 구조/기여 범위가 명확함
- 포트폴리오에 너무 서비스형 색깔이 강해지지 않음

- 본인 기여 범위를 솔직하게 설명 가능
- 대표 프로젝트 수를 늘릴 필요가 있을 때만 보조로 사용
