# 06. 스토리 뱅크

이 문서는 자기소개, About 섹션, 프로젝트 상세, 면접 대비 문구를 만들 때 재사용할 수 있는 사례 정리본이다.

---

## 1) 알고리즘이 취미가 된 계기
### 상황
- 대학 입학 후 선배와 함께 ICPC, UCPC 등에 도전
- 좋은 결과를 얻지 못했지만 문제 풀이 자체에 흥미를 느낌

### 해석
- 경쟁 결과만이 아니라 문제 해결 과정 자체를 즐김
- 이후 꾸준히 알고리즘 대회에 참가하며 실력을 키움

### 포트폴리오 연결 문장
- “알고리즘은 제게 코딩 테스트 준비가 아니라, 문제를 구조적으로 바라보는 훈련이었습니다.”
- “복잡한 문제를 빠르게 분해하고 핵심 제약을 찾는 습관은 이후 시스템 과제와 코드 분석에도 이어졌습니다.”

---

## 2) ICPC 실패 이후의 개선
### 상황
- 한 문제에 오래 매달려 다른 문제를 제대로 보지 못함
- 기대한 결과를 얻지 못함

### 행동
- 사후 복기
- 문제 선택과 시간 배분 훈련
- 꾸준한 Codeforces / AtCoder / 기타 대회 참여

### 결과
- 이후 SCPC 본선 진출 등으로 이어짐

### 해석
- 실패를 실력의 한계로 끝내지 않고 훈련 방식으로 환원함
- 이 사용자는 단순히 버티는 사람이 아니라 **복기 기반 학습**을 하는 사람으로 보이게 해야 함

---

## 3) 해커톤에서의 범위 조정
### 상황
- 랜덤 팀 구성
- 팀원 역량 차이 존재
- 짧은 시간 안에 결과물을 만들어야 함

### 행동
- 팀원별 가능한 역할 파악
- 게임 개발 방향 선택
- 필수 기능과 부가 기능을 구분
- 프로젝트 범위를 현실적으로 재조정
- 유니티 환경을 처음 접하는 팀원들이 참여할 수 있게 기본 세팅 지원

### 결과
- 제한 시간 내 완성
- 수상

### 해석
- “리더십”보다 “현실적인 범위 관리와 협업 조율”
- 협업 상황에서 목표 달성을 위해 현실적인 의사결정을 내리는 타입

---

## 4) OS / 메모리 관심의 형성
### 상황
- 전역 후 시스템 프로그래밍, 운영체제 수업 수강
- xv6 과제를 통해 커널 내부 구조를 직접 수정
- DRAM 구조 / Rowhammer 완화 / Memory X-ray 논문 학습

### 해석
- 추상적인 흥미가 아니라 학습과 탐구가 실제 행동으로 이어짐
- 시스템 소프트웨어, 메모리 관련 직무와 자연스럽게 연결 가능

### 포트폴리오 연결 문장
- “운영체제를 배우면서 소프트웨어가 하드웨어 자원을 어떻게 다루는지에 관심이 커졌고, 특히 메모리 관리와 최적화 문제에 끌리게 되었습니다.”

---

## 5) 오픈소스에 대한 관심
### 상황
- uftrace 트랙 참여
- 함수 추적, 실행 흐름, 협업 구조를 접함
- 현업 개발자들과 교류

### 해석
- 혼자 구현만 하는 타입이 아니라 공개 생태계와 도구를 통해 배우는 타입
- 장기적으로 Linux / 커널 쪽으로 성장하려는 방향성과 맞음

---

## 6) Checkhouse에서 배운 검증의 중요성
### 상황
- 팀 프로젝트 후반부
- 검증되지 않은 AI 생성 코드와 코드 리뷰 누락으로 오류가 누적
- 발표 직전 장애가 터짐

### 행동
- 문제 코드를 하나씩 땜질하지 않고 구조부터 다시 확인
- 필요한 부분은 처음부터 다시 구현
- 핵심 기능 우선순위 재정리
- 수정 후 반복 검증

### 결과
- 핵심 기능이 동작하는 수준으로 복구
- 발표/시연 마무리

### 해석
- “빠른 개발”보다 “신뢰성 있는 코드”를 더 중요하게 생각하게 된 계기
- 코드 분석, 검증, 우선순위 판단을 보여주는 대표 사례

### 포트폴리오 연결 문장
- “Checkhouse 프로젝트에서는 마감 직전 장애를 복구하며, 구조를 이해하지 못한 채 빠르게 쌓은 코드가 얼마나 쉽게 무너질 수 있는지 배웠습니다.”

---

## 7) Manbo에서의 협업과 역할 재조정
### 상황
- 팀 전체가 익숙하지 않은 기술(React Native)로 프로토타입 개발
- 시간과 학습 여유가 부족
- 일정 지연 발생

### 행동
- 문서/강의 자료를 빠르게 학습
- 팀원과 공부 방법과 노하우 공유
- 일정 기준으로 우선순위 재정리
- 역할 재분배 및 상호 보완

### 결과
- 목표 기간 안에 주요 기능 완성

### 해석
- 혼자 밀어붙이는 타입이 아니라, **부족한 부분을 메우기 위해 지식을 공유하고 협업 구조를 조정하는 타입**
- 면접/About 섹션에서 협업 성향을 보여주기 좋음

---

## 8) WOL Docker에서 배운 현실 환경의 제약
### 상황
- 원격으로 PC를 켜고 제어하는 절차를 간소화하고 싶었음
- WOL Docker 프로젝트를 진행
- Magic Packet 구조와 패킷 전송 과정을 검증

### 행동
- WOL 동작 조건을 코드뿐 아니라 네트워크 환경 단위로 확인
- 공유기 지원 여부 등 외부 조건을 점검
- 단순 기능 구현에서 끝나지 않고 실행 흐름 확장 구상

### 결과
- 실제 환경 제약을 명확히 인식
- 네트워크 기능은 코드만으로 성립하지 않는다는 점을 학습

### 해석
- 구현 자체보다 **동작 조건과 환경 의존성**을 확인하는 시각이 좋음
- 네트워크/시스템 직무 지원 시 유효한 사례

---

## 9) 학생회 타임테이블 자동화
### 상황
- 학생회 업무 중 반복되는 시간표/배치 관련 작업 존재

### 행동
- 타임테이블 자동 생성 프로그램 개발

### 결과
- 업무 편의성과 효율 향상

### 해석
- 규모는 작아도 실제 불편을 줄이는 자동화 도구를 만든 경험
- About/Experience 하단 보조 사례로 적합

---

## 10) AI 도구에 대한 태도
### 상황
- 학교 프로젝트에서 AI 생성 코드의 검증 부족을 경험
- 직접 boothmap, Family Community 등에서 AI 보조 개발 메모도 존재

### 해석
- AI를 무조건 배척하는 것이 아니라, **검증 없이 의존하면 안 된다**는 태도로 정리하는 것이 맞음
- 포트폴리오에서도 “AI를 활용했다”보다 “어디까지 직접 이해하고 수정했는가”를 보여줘야 함
